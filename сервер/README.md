# Сервер демо-CRM: памятка

Серверная часть (бэкенд). Раздаёт экран из папки `../приложение/` и отвечает на вопросы API (адреса `/api/...`). Устройство и шаги: `../план-этап-3.md`.

## Как запустить (на своём компьютере)

В терминале, находясь в папке `сервер/`:

- `npm install` — один раз: скачать готовые детали (Fastify и др.) в папку `node_modules/`.
- `npm start` — запустить сервер. В окне появятся строки журнала, окно занято, пока сервер работает.
- Открыть в браузере `http://localhost:3000` — это приложение, но уже с сервера.
- Открыть `http://localhost:3000/api/health` — ответ «сервер жив» (`ok: true`).
- `Ctrl+C` в том же окне — остановить сервер.
- `npm run dev` — то же, что `npm start`, но сервер сам перезапускается, когда вы правите его файлы.

Порт и адрес меняются переменными `PORT` и `HOST` (по умолчанию 3000 и `127.0.0.1`: сервер доступен только с этого компьютера).

## База данных (SQLite)

Файл базы: `data/crm.db` (создаётся сам при первом запуске, в git не попадает).

- `npm run db:reset` — **удалить базу и создать заново с демо-данными** (4 магазина и склад). Перед удалением переспрашивает, надо написать «да». Так делается «сброс демо».
- `npm run db:backup` — **резервная копия** базы в папку `backups/` (имя вида `crm-2026-11-12-123456.db`, время UTC). Копия проверяется на целостность, копии старше 14 дней удаляются. Папка и срок меняются переменными `BACKUP_DIR` и `BACKUP_KEEP_DAYS`. На сервере запускается раз в сутки через cron. Восстановить: остановить CRM, положить копию вместо `data/crm.db` (удалив рядом `-wal` и `-shm`), запустить CRM.
- `npm run db:migrate` — применить новые миграции, ничего не стирая. Сервер делает то же самое сам при каждом запуске.
- Посмотреть содержимое можно бесплатной программой-просмотрщиком SQLite: таблицы видны как в Excel.

В Windows PowerShell вместо `npm` пишите `npm.cmd`.

## Вход и роли

Вход по логину и ПИН (4–6 цифр). После входа сервер выдаёт «пропуск» на 12 часов (cookie `crm_session`). После 5 неверных ПИН подряд вход блокируется на 15 минут. ПИН хранится только необратимым отпечатком (хэшем).

Адреса: `POST /api/login`, `POST /api/logout`, `GET /api/me` (кто я и какие у меня права), `POST /api/me/pin` (сменить ПИН), `POST /api/staff` (создать сотрудника, только владелец), `POST /api/staff/:id/dismiss` («уволить»).

Демо-сотрудники (появляются после `npm run db:reset`): `magomed` (владелец), `ruslan` и `zaur` (старшие продавцы), `murad`, `ali`, `rashid`, `timur`, `kamil` (продавцы), `patimat` (онлайн-менеджер), `ismail` (курьер), `zarema` (бухгалтер). Один демо-ПИН на всех записан в `src/db/seed-demo.js` (строка `DEMO_PIN`). Только для демо.

На сервере за «ресепшеном» с HTTPS включить переменные `COOKIE_SECURE=1` (cookie ходит только по HTTPS) и `TRUST_PROXY=1` (сервер верит ресепшену, какой адрес у посетителя). Проверено: с ними cookie получает `Secure`, а сервер видит настоящий адрес посетителя.

**Забыл ПИН:** на сервере, в папке `сервер/`, `npm run pin:reset -- логин`. Команда ставит новый временный ПИН (печатает один раз), снимает блокировку входа и выкидывает старые пропуска; при входе ПИН надо сменить. Запись `pin_reset` попадает в журнал. Работает только на самом сервере (по SSH), через экран сбросить нельзя; «сбросить ПИН» сотруднику самим владельцем в приложении ещё не сделан.

**Первый владелец на новом сервере:** `npm run owner:create -- логин "Имя Фамилия"` (в PowerShell `npm.cmd`). Команда создаёт базу (если её нет), владельца и печатает временный ПИН один раз; при первом входе его надо сменить. Работает, только пока в базе нет владельца. Такая база считается настоящей: `npm run db:reset` на ней отказывает (даже с `--yes`), чтобы одна случайная команда не стёрла данные. Демо-база (из `db:reset`) по-прежнему сбрасывается свободно.

## Товар

`GET /api/products` — каталог целиком одним ответом: магазины, категории и товары (название, артикул, цвет, цена, размеры, остатки «доступно» по магазинам и размерам, действующие брони). Нужно право «Остатки» (`stock`). **Закупка (`costKopecks`) приходит только тем, у кого есть право «Закупочные цены» (`cost`)**, у остальных в ответе нет даже этого слова (проверено тестом). Если право «Остатки» ограничено своим магазином, чужих магазинов в ответе нет. «Доступно» = на полке минус действующая бронь (просроченная не считается). Деньги в копейках. Каталог целиком, без страниц: решение пользователя 2026-11-12; выдача частями с поиском на сервере отложена («Открытое» в `статус.md`). Замер на 25 000 вариантов: ответ 1,2 МБ, ~0,7 с.

Таблицы (миграция `0003-products.sql`): `categories`, `products` (модель), `variants` (размер), `stock` (остаток на полке по магазинам), `batches` (закупочные партии, цена последней = закупка в карточке), `holds` (брони). Демо-товары (те же 5, что в `js/data.js`) приходят из `src/db/seed-demo.js`. Ввода товаров на экране пока нет (ни создания, ни прихода, ни импорта из Excel). Чтобы на **настоящей** базе (например, на сервере в Ubuntu) было что продавать, есть команда `npm run demo:products`: она кладёт 4 демо-магазина (если магазинов ещё нет) и те же 5 демо-товаров, без сотрудников и броней. Если в базе уже есть товары, ничего не делает. Каталог теперь отдаёт ещё `shopIds` (номера магазинов) и `variantIds` у каждого товара (номера размеров, в том же порядке, что `sizes`): они нужны продаже.

## Продажа

`POST /api/sales` — оформить чек. Нужно право «Продажа» на изменение (владелец, старший продавец, продавец). Тело: `uid` (уникальный номер чека, придумывает экран), `payment` (`cash`, `card`, `transfer`), `discountPct` (скидка на весь чек, целые %), `shopId`, `items` (список `variantId` и `qty`). Всё одной неделимой операцией («всё или ничего»): сервер сам берёт цены из базы, проверяет наличие (**доступно = на полке минус действующая бронь**, забронированное не продаём), проверяет лимит скидки роли, пишет чек (`sales`) и строки (`sale_items`), списывает остаток, пишет запись `sale` в журнал. Лимит скидки: владелец без предела, старший продавец по правилу `disc_senior_pct`, остальные (продавец и свои роли) по `disc_seller_pct`. Сотрудник с магазином продаёт только в нём; у владельца магазин указывает экран; со склада не продают. Деньги в копейках; скидка раскладывается по строкам, сумма строк сходится с итогом до копейки. В каждой строке чека записаны цена и закупка «снимком» на момент продажи (для будущей прибыли; в ответ закупка не попадает). Повторная отправка того же `uid` не создаёт второй чек (ответ 200, `duplicate: true`), остаток не списывается дважды. Ошибки: 409 `not_enough` (список `shortages` с «доступно»), 403 `discount_too_high` (`maxPct`), 403 `wrong_shop`, 400 `bad_shop` и `unknown_item`, 409 `uid_conflict`. Таблицы (миграция `0004-sales.sql`): `sales`, `sale_items`. **Клиент в чеке** на сервере появится в шаге 3.7 (поле `client_id` в чеке уже есть, без ссылки). **Процент продавца** не считается при продаже: чек записывает «кто и на сколько продал», проценты считаются в шагах про зарплату и отчёты (3.9–3.10).

## Обновление сервера («выложить»)

На сервере, в папке `сервер/`: `npm run deploy`. Скрипт `scripts/deploy.sh` по порядку: делает копию базы, забирает свежий код с GitHub (`git pull --ff-only`), ставит детали (`npm ci --omit=dev`), прогоняет тесты, перезапускает службу `crm` (спросит пароль `sudo`) и проверяет, что `/api/health` отвечает. Любой шаг упал: дальше не идёт, служба не перезапускается. Порядок работы: на своём компьютере закоммитить и `git push`, затем на сервере `npm run deploy`.

## Автоматические проверки

`npm run test` — запускает проверки входа, прав, сотрудников, каталога товаров и продажи на базе в памяти (настоящая база не затрагивается). Все 26 должны быть зелёными.

## Что где лежит

- `package.json` — паспорт программы: название, команды запуска, список подключённых деталей.
- `src/app.js` — запуск сервера. `src/build-app.js` — сборка сервера (его же берут тесты).
- `src/auth/` — вход и права: `crypto.js` (хэш ПИН, пропуска), `cookies.js`, `auth.js` (вся логика входа, прав, сотрудников), `routes.js` (адреса API и «охранники» для будущих адресов).
- `src/modules/` — «комнаты» разделов; пока `products.js` (каталог товаров и остатки) и `sales.js` (продажа).
- `tests/` — автоматические проверки.
- `src/db/db.js` — подключение к базе и запуск миграций.
- `src/db/seed-demo.js` — демо-данные (магазины и сотрудники).
- `src/db/migrations/` — миграции: пронумерованные файлы «как менялась база» (`0001-core.sql` и далее). Применённые файлы не правим, только добавляем новые.
- `src/db/seed-demo.sql` — демо-данные для `db:reset` (только для показа).
- `scripts/db.js` — команды `migrate` и `reset` (с «замком» для настоящей базы).
- `scripts/create-owner.js` — команда `owner:create`, создать первого владельца.
- `scripts/demo-products.js` — команда `demo:products`, загрузить демо-товары (и демо-магазины, если их нет) в настоящую базу.
- `data/` — файл базы. В git не попадает.
- `node_modules/` — скачанные детали, появляется после `npm install`. В git не попадает.
